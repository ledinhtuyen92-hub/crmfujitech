# Phase 1D-7A Credential Security Foundation

## 1. Security Architecture
The platform integrates with Shopee, TikTok, and other platforms that issue OAuth tokens (Access Tokens and Refresh Tokens). To ensure compliance and security:
- **Plaintext Storage Prevention:** OAuth tokens must never be stored as plaintext in the database.
- **Fernet Encryption:** Symmetric encryption is utilized via `cryptography.fernet.Fernet` to safely encrypt and decrypt credentials at rest.
- **Fail-Safe Mechanism:** The application will fail-fast if `FUJITECH_PLATFORM_CREDENTIAL_KEY` is not provided in the environment.

## 2. Key Management
- **Key Source:** The encryption key is sourced strictly from the environment variable `FUJITECH_PLATFORM_CREDENTIAL_KEY`.
- **Format:** The key must be a valid 32-url-safe-base64-encoded bytes string generated by `Fernet.generate_key()`.
- **Exposure:** The key is NEVER committed to Git, logged, or hardcoded.

## 3. Encryption Flow
- **On Save:** When `PlatformAccount` is saved, the `save()` method checks if the tokens are already encrypted (by attempting to decrypt them). If they are not encrypted, it encrypts them using the Fernet key before persisting to the DB.
- **On Read (Database Level):** Database queries (e.g., in Admin or raw SQL) will only yield the encrypted ciphertext (starting with `gAAAAA...`).
- **On Read (Application Level):** Business logic uses `get_decrypted_access_token()` and `get_decrypted_refresh_token()` to securely retrieve the plaintext token in memory right before making an API call.

## 4. API & Serializer Behavior
- Currently, there are no views or serializers exposing `PlatformAccount`.
- **Future Rule:** If `PlatformAccount` is ever exposed via DRF Serializers, `access_token` and `refresh_token` MUST be added to `write_only=True` or explicitly excluded from the fields list. 
- **Rule:** Client applications (Frontend/Local Studio) must NEVER receive the plaintext tokens.

## 5. Logging Rules
- Logs MUST NOT contain the access_token or refresh_token.
- Do NOT log `PlatformAccount.__dict__` or use it in `repr()` methods recklessly. The `__str__` method explicitly only returns `display_name` and `platform`.

## 6. Key Rotation Strategy
- **Current Strategy:** A single static key is used.
- **Future Rotation:** In the event of a key compromise, a multi-key rotation strategy must be implemented where `Fernet.MultiFernet([new_key, old_key])` is utilized to gracefully decrypt old tokens and re-encrypt them with the new key.
- **Impact of Key Loss:** If the `FUJITECH_PLATFORM_CREDENTIAL_KEY` is lost, all connected shops (Shopee/TikTok) will be permanently disconnected, requiring users to re-authorize the application.

## 7. Development & Production Requirements
- **Local Development:** Developers must run `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` and add the output to their `.env` file under `FUJITECH_PLATFORM_CREDENTIAL_KEY`.
- **Production Setup:** The deployment pipeline (Docker/K8s/Env) must inject a securely generated `FUJITECH_PLATFORM_CREDENTIAL_KEY` into the backend container.

## 8. Known Limitations
- The encryption occurs at the application level (Django), meaning database backups will contain ciphertexts, but memory dumps of the Python process might still expose plaintext tokens during the brief window they are used.
- This phase only handles `PlatformAccount`. Legacy integrations (`ZaloOAConfig`, `FacebookConfig`) are out of scope for this specific phase but should eventually adopt this encryption standard.
